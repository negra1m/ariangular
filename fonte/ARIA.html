Fundamentos de Acessibilidade Angular

Primeira parte da documentação de acessibilidade para aplicações Angular, VoiceOver e TalkBack.

1. O que é acessibilidade?

Acessibilidade é a capacidade de um produto digital ser utilizado por todas as pessoas, independentemente de limitações visuais, auditivas, motoras, cognitivas ou temporárias.

Informação

Exemplos de usuários:

  • Pessoa cega usando TalkBack.
  • Pessoa cega usando VoiceOver.
  • Pessoa com baixa visão usando zoom.
  • Pessoa com mobilidade reduzida utilizando teclado.
  • Pessoa com deficiência cognitiva.
  • Pessoa com braço machucado utilizando somente uma mão.

2. WCAG 2.2

A WCAG (Web Content Accessibility Guidelines) é o conjunto mais utilizado no mundo para avaliar acessibilidade digital.

Níveis de conformidade

Nível Descrição
A Requisitos mínimos.
AA Padrão adotado pela maioria das empresas.
AAA Nível mais rigoroso.

3. POUR

Todos os critérios da WCAG derivam de quatro pilares:

P - Perceivable (Perceptível)

  • O usuário precisa conseguir perceber o conteúdo.
  • Imagens precisam de texto alternativo.
  • Informações não podem depender apenas de cor.

O - Operable (Operável)

  • A interface deve ser utilizável.
  • Compatível com teclado.
  • Compatível com leitores de tela.

U - Understandable (Compreensível)

  • Fluxos consistentes.
  • Mensagens claras.
  • Erros compreensíveis.

R - Robust (Robusto)

  • Compatível com tecnologias assistivas.
  • HTML semântico.
  • ARIA correta.

5. Como um leitor de tela enxerga uma página?

Usuários não enxergam a interface da mesma forma que usuários visuais.

Eles navegam por:

  • Títulos.
  • Botões.
  • Links.
  • Campos.
  • Landmarks.

A mesma tela, dos dois lados

Este é o HTML de um card de conta: 

<div class="card">
  <div class="titulo">Conta Corrente</div>
  <div class="saldo">R$ 4.210,00</div>
  <div class="acao" (click)="transferir()">Transferir</div>
</div>

Visualmente: um card com título, valor e botão. Impecável.

Leitura possível: 

Conta Corrente
R$ 4.210,00
Transferir

Três textos soltos. Nenhum título para navegar, nenhum botão para acionar, nenhuma forma de saber que "Transferir" faz algo. Ao navegar por títulos ou por botões, esta tela está vazia.

O mesmo card, escrito para os dois

<article class="card">
  <h2 class="titulo">Conta Corrente</h2>
  <p class="saldo">R$ 4.210,00</p>
  <button type="button" class="acao" (click)="transferir()">
    Transferir
  </button>
</article>

Leitura esperada: 

Conta Corrente, título nível 2
R$ 4.210,00
Transferir, botão

O que muda de verdade

O CSS é o mesmo. A tela é idêntica. O que mudou foi a árvore de acessibilidade — a estrutura paralela que o navegador constrói e entrega ao leitor de tela.

Ela não vem das classes nem do visual. Vem das tags e dos atributos. É por isso que trocar div por h2 e button não é preciosismo: é a diferença entre existir e não existir para uma parte das pessoas.

Veja a sua

No Chrome: F12, aba Elements, painel Accessibility. No Firefox: F12, aba Acessibilidade. É a página como o leitor de tela recebe — e costuma ser uma surpresa desconfortável na primeira vez.

Atenção

Uma tela visualmente perfeita pode ser completamente inutilizável para um leitor de tela.

8. Landmarks

Landmarks permitem que leitores de tela naveguem rapidamente pelas regiões importantes da página.

Tag Função
header Cabeçalho.
nav Navegação.
main Conteúdo principal.
aside Conteúdo complementar.
footer Rodapé.

✅ Correto — a estrutura completa de uma tela

<a class="pular" href="#conteudo">Pular para o conteúdo</a>

<header>
  <!-- Duas navegações na mesma página precisam de nomes
       diferentes, senão o leitor lista "navegação, navegação". -->
  <nav aria-label="Principal">
    <a routerLink="/extrato">Extrato</a>
    <a routerLink="/pix">Pix</a>
  </nav>
</header>

<main id="conteudo" tabindex="-1">
  <h1>Extrato</h1>
  <!-- ... -->
</main>

<aside aria-label="Ofertas">
  <!-- ... -->
</aside>

<footer>
  <nav aria-label="Rodapé">
    <a routerLink="/ajuda">Ajuda</a>
  </nav>
</footer>

Leitura esperada, ao listar as regiões: 

Banner
Navegação, Principal
Principal
Complementar, Ofertas
Rodapé de página
Navegação, Rodapé

Um main por página

<main> é o destino do "pular para o conteúdo" e o ponto de partida de quem navega por regiões. Dois na mesma página tornam o atalho ambíguo, e o leitor passa a perguntar qual deles.

❌ Evitar

<div class="header">
  <div class="nav"><!-- ... --></div>
</div>
<div class="conteudo"><!-- ... --></div>

Sem landmark, a única forma de chegar ao conteúdo é percorrer a página inteira desde o topo — a cada visita, em toda tela.

13. Erros mais comuns encontrados em Angular

  • Div clicável simulando botão.
  • Ícone clicável sem aria-label.
  • Input apenas com placeholder.
  • Ausência de heading principal.
  • Modal sem gerenciamento de foco.
  • Erros de formulário não anunciados.
  • Uso excessivo de ARIA.
  • Links agindo como botão.
  • Botões agindo como links.
  • tabindex positivo.

Os dez, com a correção ao lado

<!-- ❌ 1. div clicável -->
<div (click)="salvar()">Salvar</div>
<!-- ✅ -->
<button type="button" (click)="salvar()">Salvar</button>
<!-- ❌ 2. ícone sem nome -->
<button><mat-icon>delete</mat-icon></button>
<!-- ✅ -->
<button aria-label="Excluir item">
  <mat-icon aria-hidden="true">delete</mat-icon>
</button>
<!-- ❌ 3. só placeholder -->
<input placeholder="E-mail">
<!-- ✅ -->
<label for="email">E-mail</label>
<input id="email" type="email">
<!-- ❌ 4. sem heading principal -->
<div class="titulo">Extrato</div>
<!-- ✅ -->
<h1>Extrato</h1>
<!-- ❌ 5. modal sem foco -->
<div class="modal" *ngIf="aberto"></div>
<!-- ✅ -->
<dialog #d aria-labelledby="t"><h2 id="t">Confirmar</h2></dialog>
<!-- + d.showModal() ao abrir, e devolver o foco ao fechar -->
<!-- ❌ 6. erro não anunciado -->
<span *ngIf="invalido" class="erro">CPF inválido</span>
<!-- ✅ região já no DOM, ligada ao campo -->
<input [attr.aria-describedby]="invalido ? 'e' : null"
       [attr.aria-invalid]="invalido">
<span id="e" role="alert">{{ invalido ? 'CPF inválido' : '' }}</span>
<!-- ❌ 7. ARIA em excesso -->
<button role="button" aria-label="Salvar">Salvar</button>
<!-- ✅ -->
<button>Salvar</button>
<!-- ❌ 8. link que age como botão -->
<a href="#" (click)="excluir()">Excluir</a>
<!-- ✅ link navega, botão executa -->
<button type="button" (click)="excluir()">Excluir</button>
<!-- ❌ 9. botão que age como link -->
<button (click)="router.navigate(['/extrato'])">Extrato</button>
<!-- ✅ -->
<a routerLink="/extrato">Extrato</a>
<!-- ❌ 10. tabindex positivo -->
<input tabindex="3">
<!-- ✅ a ordem vem do DOM; 0 entra na sequência, -1 sai dela -->
<input>

O tabindex positivo é o pior da lista porque contamina a página inteira: qualquer valor maior que zero salta na frente de todos os elementos naturais, inclusive os de outros componentes.

Antes de escrever a role: já existe tag para isso?

Metade da tabela acima você nunca precisa digitar, porque o HTML já entrega — com teclado e estado incluídos.

Em vez de Use O que ganha de graça
role="button" <button> Tab, Enter, Espaço, disabled.
role="link" <a href> Tab, Enter, abrir em nova aba.
role="checkbox" <input type="checkbox"> Espaço, estado sincronizado.
role="dialog" <dialog> Foco preso, ESC, inerte atrás.
role="progressbar" <progress> Valor anunciado sozinho.
role="list" <ul> e <li> "lista com N itens".

As que não têm equivalente nativo

Estas você escreve mesmo, porque o HTML não tem tag para elas. São também as que exigem mais teclado escrito à mão — e onde o @angular/aria passa a valer mais que a implementação própria. 

role="tablist"  role="tab"  role="tabpanel"
role="menu"     role="menuitem"
role="listbox"  role="option"
role="alert"    role="status"

role muda o que se anuncia, não o que acontece

<!-- ❌ anuncia "botão", não aciona com teclado -->
<div role="button" (click)="salvar()">Salvar</div>

Este é o mal-entendido mais caro sobre ARIA. A role é uma etiqueta para a tecnologia assistiva. Ela não adiciona comportamento nenhum — e prometer um botão que não funciona é pior do que não prometer nada.

26. Erros mais comuns com ARIA

  • Adicionar role="button" em botão.
  • Adicionar aria-label desnecessária.
  • aria-hidden em conteúdo importante.
  • aria-live em excesso.
  • Estado aria-expanded desatualizado.
  • aria-describedby apontando para id inexistente.
  • Criar componente customizado sem teclado.

Cada erro, lado a lado

<!-- ❌ role redundante: button já é button -->
<button role="button">Salvar</button>

<!-- ✅ -->
<button>Salvar</button>
<!-- ❌ o aria-label SUBSTITUI o texto visível.
     Quem usa comando de voz diz "clicar em Salvar" e nada acontece,
     porque o nome real virou "Salvar formulário". -->
<button aria-label="Salvar formulário">Salvar</button>

<!-- ✅ o texto visível já é o nome -->
<button>Salvar</button>
<!-- ❌ some da árvore de acessibilidade, mas o Tab continua chegando:
     a pessoa foca um botão que não é anunciado -->
<button aria-hidden="true">Fechar</button>

<!-- ✅ esconda o ícone, nunca o controle -->
<button aria-label="Fechar">
  <svg aria-hidden="true"><!-- ... --></svg>
</button>
<!-- ❌ valor fixo: anuncia "recolhido" para sempre -->
<button aria-expanded="false" (click)="alternar()">Detalhes</button>

<!-- ✅ ligado ao estado real -->
<button [attr.aria-expanded]="aberto()" (click)="alternar()">Detalhes</button>
<!-- ❌ id que não existe: o leitor não lê descrição nenhuma,
     e não avisa que a referência quebrou -->
<input aria-describedby="dica-cpf">

<!-- ✅ o id existe no DOM -->
<input aria-describedby="dica-cpf">
<p id="dica-cpf">Apenas números</p>

O erro que não aparece em ferramenta nenhuma

Todos acima o axe encontra. Este não: 

<div role="button" tabindex="0" (click)="salvar()">Salvar</div>

Tem role, tem tabindex, tem nome. O axe aprova. E Enter e Espaço não acionam nada, porque role="button" não traz comportamento — só muda o que é anunciado.

O resultado é pior que a div nua: o leitor de tela promete um botão que não funciona. Informação falsa com confiança.

A regra que evita a lista inteira

Antes de escrever qualquer atributo ARIA, pergunte se existe elemento HTML que já faz aquilo. Na maioria esmagadora dos casos existe, e ele vem com teclado, estado e semântica de graça.

Formulários Acessíveis

Formulários são uma das áreas com mais problemas de acessibilidade.

Os princípios básicos são:

  • Todo campo precisa de label.
  • Todo erro precisa ser anunciado.
  • Todo campo obrigatório deve informar essa condição.
  • A navegação por teclado deve funcionar.
  • O foco deve ir para o erro ou mensagem importante.

Label

✅ Correto

<label for="nome">
Nome
</label>

<input
id="nome"
type="text">

Erro que aparece depois do envio precisa de região viva. Sem ela, quem usa leitor de tela não fica sabendo que ele existe.

A armadilha da região que ainda não existe

Este é o erro mais comum de todos, e ele parece certo no código:

Não funciona. role="alert" e aria-live avisam o leitor de tela quando o conteúdo da região muda. Se a região inteira só entra no DOM no momento do erro, não houve mudança de conteúdo para observar — houve o nascimento de um elemento novo, que o leitor não estava monitorando.

Vale para *ngIf, para @if e para o <mat-error> do Angular Material, que tem role="alert" por dentro e esbarra exatamente nisso.

✅ Correto — região sempre no DOM

     O leitor de tela já está observando quando o texto chega. -->

Pausar não é opcional

Conteúdo que se move sozinho por mais de 5 segundos precisa ter como parar. É critério de nível A — o mais básico da WCAG (2.2.2). Carrossel que gira sem botão de pausa é falha, não questão de gosto.

O motivo não é só leitor de tela: quem tem dislexia ou déficit de atenção perde a linha quando algo se mexe ao lado do texto que está lendo.

mover(de: number, delta: number): void {
  const para = de + delta;
  const lista = [...this.tarefas()];
  const [item] = lista.splice(de, 1);
  lista.splice(para, 0, item);
  this.tarefas.set(lista);

  // Sem anúncio, a pessoa não tem como saber que funcionou:
  // o item mudou de lugar numa lista que ela não vê.
  this.announcer.announce(
    `${item.titulo} movido para a posição ${para + 1} de ${lista.length}`,
    'polite',
  );

  // O foco tem que seguir o item, não a posição.
  queueMicrotask(() => this.botoes()[para]?.nativeElement.focus());
}

Aplicações SPA não recarregam a página.

O leitor de tela não percebe automaticamente que houve mudança de tela.

O que se perde quando a página não recarrega

Num carregamento normal, o navegador entrega três coisas de graça. No SPA, as três param de acontecer e viram trabalho seu.

O navegador fazia No SPA Quem resolve
Reposicionar o foco no topo. O foco fica no link acionado, que já não existe. Serviço de foco de rota.
Anunciar o título da nova página. Silêncio total. LiveAnnouncer ou TitleStrategy.
Atualizar o título da aba. Fica o título da primeira tela. Title ou TitleStrategy.

✅ Correto — título por rota

O título da aba é o primeiro texto que muitos leitores de tela anunciam ao trocar de contexto. Deixar o mesmo em todas as telas faz a pessoa perder a referência de onde está. 

export const routes: Routes = [
  { path: 'extrato', component: Extrato, title: 'Extrato — Banco' },
  { path: 'pix', component: Pix, title: 'Área Pix — Banco' },
];

Para título dinâmico, uma TitleStrategy resolve para toda a aplicação: 

@Injectable({ providedIn: 'root' })
export class TituloDaRota extends TitleStrategy {

  private readonly title = inject(Title);

  override updateTitle(snapshot: RouterStateSnapshot): void {
    const titulo = this.buildTitle(snapshot);
    this.title.setTitle(titulo ? `${titulo} — Banco` : 'Banco');
  }

}
providers: [
  { provide: TitleStrategy, useClass: TituloDaRota },
]

import { Injectable, inject, DOCUMENT } from '@angular/core';
import { Router, NavigationEnd } from '@angular/router';
import { LiveAnnouncer } from '@angular/cdk/a11y';
import { filter } from 'rxjs';

@Injectable({ providedIn: 'root' })
export class RouteFocusService {

  private readonly router = inject(Router);
  private readonly doc = inject(DOCUMENT);
  private readonly announcer = inject(LiveAnnouncer);

  start(): void {
    this.router.events
      .pipe(filter((e) => e instanceof NavigationEnd))
      .subscribe(() => this.aoTrocarDeTela());
  }

  private aoTrocarDeTela(): void {
    // Mudança só de âncora não é troca de tela: mover o foco
    // aqui tiraria a pessoa do lugar onde ela acabou de chegar.
    if (this.router.url.includes('#')) return;

    const alvo =
      this.doc.querySelector<HTMLElement>('main h1') ??
      this.doc.getElementById('conteudo');

    if (!alvo) return;

    // tabindex -1 permite foco por código sem entrar na ordem do Tab.
    if (!alvo.hasAttribute('tabindex')) alvo.setAttribute('tabindex', '-1');
    alvo.focus({ preventScroll: false });

    // O anúncio vem DEPOIS do foco. Na ordem inversa, mover o
    // foco interrompe a fala e a pessoa ouve a frase pela metade.
    this.announcer.announce(alvo.textContent?.trim() ?? '', 'polite');
  }

}

Ligando no componente raiz: 

export class App {
  constructor() {
    inject(RouteFocusService).start();
  }
}

Três detalhes que decidem se funciona

  • Ignorar mudança de âncora. Clicar num link interno da mesma página dispara evento de rota. Sem a guarda, o foco pula para o topo e a pessoa perde o trecho que pediu para ver.
  • Anunciar depois de focar. Mover o foco cancela a fala em andamento. Anunciar antes faz o texto ser cortado no meio.
  • tabindex="-1", nunca 0. Com 0 o título entra na ordem do Tab e vira uma parada extra em toda navegação por teclado, sem fazer nada.

A armadilha do texto repetido

Chamar duas vezes seguidas com o mesmo texto anuncia uma vez só. A região viva recebe a mesma string, não houve mudança de conteúdo, e o leitor de tela não tem o que reanunciar. 

// ❌ o segundo anúncio não acontece
this.announcer.announce('Item adicionado');
this.announcer.announce('Item adicionado');

É a causa de "o anúncio funcionou no primeiro clique e depois parou" — o código está certo, o comportamento é esperado.

A correção é fazer a mensagem carregar o que mudou de verdade. Quase sempre isso deixa o anúncio melhor, não pior: 

// ✅ a contagem muda, então o texto muda
this.announcer.announce(`Item adicionado. ${this.total()} no carrinho.`);

Quando não há nada que varie, limpar a região antes força o anúncio. 

this.announcer.clear();
this.announcer.announce('Item adicionado');

❌ Evitar

this.announcer.announce('Salvo', 'assertive');

assertive interrompe a leitura em andamento. Numa confirmação de sucesso isso corta a frase que a pessoa estava ouvindo para dizer algo que podia esperar dois segundos. Reserve para erro que bloqueia o fluxo.

Quando usar LiveAnnouncer

  • Pagamento concluído.
  • Filtro aplicado.
  • Busca concluída.
  • Upload concluído.
  • Erro importante.

A regra por trás da lista

Anuncie quando o resultado acontece sem trocar de tela e sem mover o foco. Se a pessoa vai perceber pelo foco que chegou em outro lugar, o anúncio vira repetição.

Situação Anunciar? Por quê
Filtro aplicado, lista atualizou na mesma tela. Sim Nada indica que mudou.
Item removido do carrinho. Sim O elemento sumiu sem aviso.
Modal abriu e recebeu foco. Não O foco já anuncia o dialog.
Campo ficou inválido ao sair dele. Não Anuncia ao voltar o foco no campo.
Botão virou "Salvando…". Não Foco está no botão, muda sozinho.

✅ Correto — filtro em lista

aplicarFiltro(termo: string): void {
  this.resultados.set(this.buscar(termo));

  const n = this.resultados().length;

  this.announcer.announce(
    n === 0
      ? 'Nenhum resultado para ' + termo
      : `${n} ${n === 1 ? 'resultado' : 'resultados'} para ${termo}`,
    'polite',
  );
}

Leitura esperada: 

12 resultados para transferência

❌ Evitar — anunciar a cada tecla

onInput(valor: string): void {
  this.announcer.announce(`${this.buscar(valor).length} resultados`);
}

Num campo de busca, isso dispara um anúncio por caractere digitado. O leitor de tela vira uma metralhadora e a pessoa não consegue nem terminar de escrever. Use debounce de uns 400ms — o tempo de parar de digitar.

cdkTrapFocus

Prende o foco em uma região.

Ideal para:

  • Modal.
  • Bottom Sheet.
  • Dialog.

✅ Correto — overlay completo

Prender o foco é metade do trabalho. As outras metades são devolver o foco ao fechar e tornar o resto da página inalcançável. 

@Component({
  imports: [A11yModule],
  template: `
    <button #abridor (click)="abrir()">Filtros</button>

    @if (aberto()) {
      <div
        class="painel"
        role="dialog"
        aria-modal="true"
        aria-labelledby="filtros-titulo"
        cdkTrapFocus
        [cdkTrapFocusAutoCapture]="true"
        (keydown.escape)="fechar()"
      >
        <h2 id="filtros-titulo">Filtros</h2>
        <!-- ... -->
        <button (click)="fechar()">Aplicar</button>
      </div>
    }
  `,
})
export class Filtros {

  private readonly abridor = viewChild<ElementRef<HTMLElement>>('abridor');

  protected readonly aberto = signal(false);

  protected abrir(): void {
    this.aberto.set(true);
    // O conteúdo de trás sai da árvore de acessibilidade.
    // Sem isto, o leitor de tela continua lendo o que está atrás.
    document.getElementById('conteudo')?.setAttribute('inert', '');
  }

  protected fechar(): void {
    this.aberto.set(false);
    document.getElementById('conteudo')?.removeAttribute('inert');

    // Devolver o foco é obrigatório: sem isso ele cai no body
    // e a pessoa recomeça a página do zero.
    this.abridor()?.nativeElement.focus();
  }

}

FocusMonitor

Identifica como o foco chegou até o elemento.

  • Mouse.
  • Teclado.
  • Touch.
  • Programático.

✅ Correto

import { FocusMonitor } from '@angular/cdk/a11y';

export class Cartao implements AfterViewInit, OnDestroy {

  private readonly monitor = inject(FocusMonitor);
  private readonly el = inject(ElementRef<HTMLElement>);

  ngAfterViewInit(): void {
    this.monitor
      .monitor(this.el, true) // true = observa os filhos também
      .subscribe((origem) => {
        // 'keyboard' | 'mouse' | 'touch' | 'program' | null
        this.el.nativeElement.classList.toggle(
          'foco-visivel',
          origem === 'keyboard',
        );
      });
  }

  ngOnDestroy(): void {
    // Obrigatório: sem isto o monitor vaza a cada componente destruído.
    this.monitor.stopMonitoring(this.el);
  }

}

Antes de usar: você precisa mesmo disto?

O caso mais comum — mostrar o anel de foco só para quem navega por teclado — o CSS resolve sozinho, sem nenhum código: 

button:focus-visible {
  outline: 3px solid var(--cor-foco);
  outline-offset: 3px;
}

:focus-visible é suportado em todos os navegadores atuais e já aplica a heurística de "chegou por teclado". O FocusMonitor vale quando a decisão precisa acontecer no TypeScript, não no estilo: registrar analytics, escolher para onde mandar o foco seguinte, mudar comportamento por origem.

❌ Evitar

button:focus {
  outline: none;
}

Remover o contorno sem substituto é o erro mais comum de todos. Para quem navega por teclado, equivale a esconder o cursor do mouse: a pessoa perde o rastro de onde está (WCAG 2.4.7).

FocusKeyManager

Gerencia navegação por setas.

Muito utilizado em:

  • Tabs.
  • Menus.
  • Listbox.
  • Combobox.

Antes de escrever: já existe pronto?

Desde o Angular v22, @angular/aria entrega listbox, menu, tabs e combobox como diretiva, com teclado e ARIA implementados segundo a especificação. Escrever à mão só se justifica quando nenhum padrão de lá serve.

O que vem abaixo é para esse caso — e para entender o que a diretiva faz por baixo.

✅ Correto — os três passos

O padrão é sempre o mesmo: consultar as opções, inicializar o manager, encaminhar o teclado para ele. 

import { Component, viewChildren, AfterViewInit, inject } from '@angular/core';
import { FocusKeyManager, FocusableOption } from '@angular/cdk/a11y';

@Component({
  selector: 'app-lista-opcoes',
  template: `
    <!-- O contêiner escuta o teclado. Cada opção é um item. -->
    <ul role="listbox" tabindex="0" (keydown)="aoTeclar($event)">
      <li
        app-opcao
        role="option"
        *ngFor="let item of itens"
        [attr.aria-selected]="item === selecionado"
      >
        {{ item.nome }}
      </li>
    </ul>
  `,
})
export class ListaOpcoes implements AfterViewInit {

  // 1. as opções
  private readonly opcoes = viewChildren(Opcao);

  private manager!: FocusKeyManager<Opcao>;

  ngAfterViewInit(): void {
    // 2. o manager
    this.manager = new FocusKeyManager(this.opcoes())
      .withWrap()        // da última volta para a primeira
      .withTypeAhead();  // digitar "sa" pula para "Salvador"
  }

  // 3. encaminhar o teclado
  aoTeclar(event: KeyboardEvent): void {
    this.manager.onKeydown(event);
  }

}

Cada opção precisa implementar FocusableOption — é o contrato que o manager usa para mover o foco. 

@Directive({ selector: '[app-opcao]' })
export class Opcao implements FocusableOption {

  private readonly el = inject(ElementRef<HTMLElement>);

  // O manager chama isto. Sem ele, nada se move.
  focus(): void {
    this.el.nativeElement.focus();
  }

  // Usado pelo withTypeAhead.
  getLabel(): string {
    return this.el.nativeElement.textContent?.trim() ?? '';
  }

}

FocusKeyManager ou ListKeyManager?

Classe O que faz Quando usar
FocusKeyManager Move o foco de verdade para cada item. Menu e toolbar, onde o item recebe foco.
ActiveDescendantKeyManager Marca o item ativo sem tirar o foco do campo. Combobox, onde o foco fica no input.
ListKeyManager Base das duas. Só controla o índice ativo. Quando o comportamento de foco é seu.

❌ Evitar

<li role="option" tabindex="0" (click)="selecionar(item)">
  {{ item.nome }}
</li>

Dar tabindex="0" a cada opção transforma uma lista de 40 itens em 40 paradas do Tab. O padrão correto é o contêiner receber o Tab uma vez, e as setas moverem dentro dele.

O que vem pronto

<button mat-icon-button><mat-icon>delete</mat-icon></button>

<button mat-icon-button aria-label="Excluir lançamento">

Contraste do tema não é verificado por ninguém

Um tema customizado passa a compilar com qualquer cor. Nada avisa que o texto ficou em 3:1. 

// Verifique os pares do seu tema antes de subir.
// A conta é a razão de contraste da WCAG:
// texto normal precisa de 4.5:1, texto grande e borda de 3:1.

Ícone dentro de componente é sempre decorativo

Vale para botão, aba, item de menu, chip e campo. Se o ícone acompanha texto, ele é redundante; se está sozinho, o nome vai no controle, não nele. 

<mat-icon aria-hidden="true">home</mat-icon>

Sem isso, o leitor de tela anuncia o nome da ligadura da fonte: "home", "delete", "more_vert" — que é o identificador interno, não a função.

O foco que não volta

O problema mais reportado do MatDialog: ao fechar, o foco vai para o início do documento em vez de voltar ao botão que abriu. Quem usa leitor de tela perde o lugar e precisa percorrer a página inteira de novo.

O restoreFocus: true resolve a maior parte dos casos. Quando o botão que abriu deixa de existir — uma linha de tabela que some depois da ação, por exemplo — é preciso escolher o destino na mão. 

const ref = this.dialog.open(ConfirmarPagamento, {

ref.afterClosed().subscribe(() => {

Sem ariaLabelledBy o dialog abre sem nome acessível: o leitor de tela anuncia apenas "diálogo", e a pessoa não sabe o que está confirmando.

Lazy Loading

Quando conteúdo aparece após carregamento assíncrono, o foco e o anúncio devem ser avaliados.

✅ Correto — @defer com estado anunciado

@defer (on viewport) {

  <app-grafico-gastos />

} @placeholder {

  <p>Gráfico de gastos</p>

} @loading (after 100ms; minimum 500ms) {

  <!-- role="status" faz o leitor anunciar sem roubar o foco.
       O aria-busy diz que a região ainda não terminou. -->
  <p role="status" aria-busy="true">Carregando gráfico de gastos</p>

} @error {

  <p role="alert">Não foi possível carregar o gráfico. Tente novamente.</p>

}

Leitura esperada: 

Carregando gráfico de gastos

Os dois parâmetros que evitam o pior

  • after 100ms — não mostra o "carregando" se a resposta vier rápido. Sem isso, um flash aparece e some, e o leitor de tela anuncia algo que já não existe.
  • minimum 500ms — se aparecer, fica tempo suficiente para ser lido. Um estado que dura 80ms é ruído, não informação.

Onde o foco deve ficar

A regra depende de quem pediu o carregamento:

Situação O foco
Carregou ao entrar na viewport. Não move. Ninguém pediu.
Pessoa clicou em "ver detalhes". Move para o conteúdo novo.
Erro depois de uma ação. Move para a mensagem de erro.

❌ Evitar

@loading {
  <mat-spinner />
}

Spinner sem texto não diz nada a quem não vê a tela. O silêncio durante a espera é indistinguível de página quebrada — e depois de alguns segundos a pessoa desiste.

Signals e Acessibilidade

Signals atualizam a UI automaticamente.

Mas leitores de tela não são notificados automaticamente.

Use:

  • aria-live
  • LiveAnnouncer

Onde o mal-entendido mora

Signal atualiza o DOM. Atualizar o DOM não avisa ninguém. Um contador que vai de 3 para 4 muda na tela e não produz som nenhum — a menos que aquele pedaço de DOM esteja numa região viva declarada.

✅ Correto — região viva no template

@Component({
  template: `
    <button (click)="adicionar()">Adicionar ao carrinho</button>

    <!-- role="status" é uma região viva polite pronta.
         O signal atualiza o texto; a região faz o anúncio. -->
    <p role="status">{{ itens() }} itens no carrinho</p>
  `,
})
export class Carrinho {

  protected readonly itens = signal(0);

  protected adicionar(): void {
    this.itens.update((n) => n + 1);
  }

}

Leitura esperada: 

4 itens no carrinho

✅ Correto — effect quando não há texto na tela

Quando a mudança não tem representação visual em texto, o effect conecta o signal ao anúncio. 

export class Filtros {

  private readonly announcer = inject(LiveAnnouncer);

  readonly resultados = signal<Item[]>([]);

  constructor() {
    effect(() => {
      const n = this.resultados().length;
      this.announcer.announce(`${n} resultados`, 'polite');
    });
  }

}

❌ Evitar — effect sem freio

effect(() => {
  this.announcer.announce(this.termoBusca());
});

O effect roda a cada mudança do signal. Ligado num campo de texto, isso é um anúncio por tecla digitada. Use um signal derivado que mude com menos frequência, ou debounce.

Nada mudou com signals

Signals não têm regra de acessibilidade própria. O que muda é que a atualização ficou mais fácil de escrever — e, com isso, ficou mais fácil atualizar a tela em lugares onde antes ninguém mexia. Cada um desses lugares é um anúncio a decidir.

✅ Correto — quando o customizado é inevitável

Se a estilização exige um elemento próprio, replique o contrato inteiro. Este é o mínimo de um botão feito à mão: 

@Component({
  selector: 'app-botao',
  host: {
    'role': 'button',
    '[attr.tabindex]': 'desabilitado() ? -1 : 0',
    '[attr.aria-disabled]': 'desabilitado()',
    '(click)': 'acionar()',
    '(keydown.enter)': 'acionar()',
    '(keydown.space)': 'acionar($event)',
  },
  template: `<ng-content />`,
})
export class Botao {

  readonly desabilitado = input(false);
  readonly acionado = output<void>();

  protected acionar(event?: Event): void {
    // Espaço rola a página por padrão. Num botão, não pode.
    event?.preventDefault();
    if (this.desabilitado()) return;
    this.acionado.emit();
  }

}

Em novembro de 2025, com o Angular v22, o time Angular lançou o pacote oficial Angular Aria.

Este é o lançamento mais relevante para acessibilidade na história do Angular. Combobox, listbox, menu e tree são os componentes que mais geram bug de acessibilidade quando feitos à mão — e agora existe uma implementação oficial, mantida pelo time do framework, seguindo a especificação.

Sequência de Foco

A ordem do DOM deve refletir a ordem visual.

Usuários de leitor de tela navegam seguindo a estrutura da página.

O CSS que quebra a ordem sem avisar

order, row-reverse e grid-area mudam o que se vê, e não mudam o DOM. O resultado: a pessoa vê "Cancelar, Confirmar" e o Tab entrega "Confirmar, Cancelar". 

<!-- ❌ o visual inverte, o Tab não -->
<div class="acoes">
  <button>Confirmar</button>
  <button>Cancelar</button>
</div>
.acoes {
  display: flex;
  flex-direction: row-reverse;
}

É uma falha de WCAG 1.3.2, e das mais difíceis de perceber: para quem enxerga, a tela está perfeita.

✅ Correto — arrume o DOM, não o CSS

<div class="acoes">
  <button>Cancelar</button>
  <button>Confirmar</button>
</div>
.acoes {
  display: flex;
  justify-content: flex-end;
}

Quando o DOM precisa divergir de propósito

Barra lateral que aparece à esquerda mas deve ser lida depois do conteúdo é um caso legítimo. A saída é colocar no DOM na ordem de leitura e posicionar por grid — nunca o contrário. 

<div class="pagina">
  <main><!-- primeiro no DOM: é o que importa --></main>
  <aside><!-- depois --></aside>
</div>
.pagina {
  display: grid;
  grid-template-columns: 16rem 1fr;
}
/* O aside vai para a coluna 1 sem sair do lugar no DOM. */
.pagina aside { grid-column: 1; grid-row: 1; }
.pagina main  { grid-column: 2; grid-row: 1; }

✅ Correto — o dialog nativo faz quase tudo

<dialog> com showModal() entrega role, aria-modal, foco preso e ESC já implementados e testados pelo navegador. Reimplementar isso à mão é a origem clássica de modal inacessível. 

@Component({
  template: `
    <button #abridor (click)="abrir()">Excluir conta</button>

    <dialog #dialog (close)="aoFechar()" aria-labelledby="excluir-titulo">

      <h2 id="excluir-titulo">Excluir conta</h2>
      <p>Esta ação não pode ser desfeita.</p>

      <button (click)="dialog.close()">Cancelar</button>
      <button (click)="confirmar()">Excluir</button>

    </dialog>
  `,
})
export class ExcluirConta {

  private readonly dialog = viewChild<ElementRef<HTMLDialogElement>>('dialog');
  private readonly abridor = viewChild<ElementRef<HTMLElement>>('abridor');

  protected abrir(): void {
    // showModal(), não show(): só ele torna o resto inerte.
    this.dialog()?.nativeElement.showModal();
  }

  protected aoFechar(): void {
    // A única parte que o navegador não faz sozinho.
    this.abridor()?.nativeElement.focus();
  }

}

A regra que sobrevive aos dois

Não escreva para um leitor de tela específico. Escreva HTML semântico correto e ARIA mínima — é o que os dois interpretam igual. Toda vez que algo funciona só em um deles, quase sempre é sinal de que a solução está apoiada num comportamento específico, e não na especificação.

Testar em um não cobre o outro

São motores diferentes, com heurísticas diferentes, em navegadores diferentes. A combinação que importa em produção: TalkBack com Chrome no Android, VoiceOver com Safari no iOS. Testar VoiceOver no Mac com Chrome não representa nem um nem outro.

O modo por títulos é o mais revelador

Antes de percorrer elemento por elemento, mude a navegação para "títulos" e desça a página. Em 20 segundos você descobre se a estrutura faz sentido — e é assim que quem usa leitor de tela de verdade se orienta numa página nova. Ninguém percorre 200 elementos um a um.

Se ao navegar por títulos você não consegue dizer do que a página trata, a estrutura está errada, independente do que o axe disser.

Como achar os quatro primeiros em cinco minutos

Sem instalar nada, no console do navegador: 

// Botões e links sem nome acessível
document.querySelectorAll('button, a').forEach((el) => {
  const nome = (
    el.getAttribute('aria-label') ??
    el.textContent ??
    ''
  ).trim();
  if (!nome) console.warn('sem nome:', el);
});

// Campos sem label associado
document.querySelectorAll('input, select, textarea').forEach((el) => {
  const temLabel =
    el.labels?.length ||
    el.getAttribute('aria-label') ||
    el.getAttribute('aria-labelledby');
  if (!temLabel) console.warn('sem label:', el);
});

// tabindex positivo
document.querySelectorAll('[tabindex]').forEach((el) => {
  if (Number(el.getAttribute('tabindex')) > 0) console.warn('tabindex+:', el);
});

Isso não substitui axe nem teste real — pega três classes de erro das mais comuns, e roda em qualquer página em segundos.

Por que estes são críticos e não altos

O corte é um só: a pessoa não conclui a jornada. Não é "fica ruim", é "não dá para terminar". Cada exemplo abaixo trava um fluxo inteiro. 

<!-- Botão principal sem nome.
     Anunciado: "botão". A pessoa não confirma o pagamento
     porque não sabe que aquilo confirma o pagamento. -->
<button (click)="confirmar()">
  <mat-icon>check</mat-icon>
</button>
<!-- Modal inacessível.
     Abre, o foco não entra, o leitor continua na página de trás.
     A pessoa não sabe que existe algo para confirmar. -->
<div class="modal" *ngIf="aberto">
  <button (click)="excluirConta()">Confirmar exclusão</button>
</div>
<!-- Erro não anunciado.
     O envio falha em silêncio. A pessoa espera uma confirmação
     que nunca vem, tenta de novo, e desiste. -->
<span *ngIf="erro" class="erro">{{ erro }}</span>
<!-- Foco preso incorretamente.
     cdkTrapFocus sem forma de sair: nem ESC, nem botão fechar.
     A pessoa fica presa até recarregar a página. -->
<div cdkTrapFocus>
  <p>Carregando…</p>
</div>
<!-- Campo sem label.
     "campo de edição". Num cadastro de 8 campos iguais,
     não há como saber qual é qual. -->
<input type="text" placeholder="CPF">

O teste de severidade

Pergunte: desligando o monitor, uma pessoa consegue concluir esta tarefa?

  • Não consegue de jeito nenhum: crítico.
  • Consegue com muita dificuldade ou tentativa e erro: alto.
  • Consegue, mas a experiência é pior: médio.
  • Consegue normalmente, há algo a melhorar: baixo.

Exemplos de Bugs Médios

  • Heading incorreto.
  • Texto alternativo ruim.
  • Tooltip sem descrição.
  • Leitura redundante.

European Accessibility Act

Desde 28 de junho de 2025 o European Accessibility Act é exigível em todos os países da União Europeia.

Ele deixou de ser assunto só de quem vende para a Europa. Empresas brasileiras que atendem clientes europeus, ou que fazem parte da cadeia de fornecimento de uma empresa europeia, entram no escopo.

Categoria Exemplos
Comércio eletrônico Loja, checkout, área do cliente.
Serviços bancários Internet banking, aplicativo, autenticação.
Transporte Venda de passagem, informação de viagem.
Comunicação Telefonia, mensagens, chamada de emergência.
Livros e mídia Leitores digitais, streaming.

A norma técnica

A conformidade é avaliada pela EN 301 549, que incorpora a WCAG. A versão 4.1.1 está prevista para 2026.

Informação

Na prática, atender WCAG 2.2 nível AA cobre a maior parte do que a norma exige para conteúdo web. É o mesmo alvo que este guia inteiro persegue.

O que muda no dia a dia

  • Acessibilidade deixa de ser melhoria e passa a ser requisito de entrada.
  • Exige documentação de conformidade, não só o site funcionando.
  • Pode ser cobrada em contrato e em processo de compra.
  • Aplica-se a produto novo e a atualização de produto existente.

O que fazer

  1. Levantar se o produto atende clientes na União Europeia.
  2. Auditar contra WCAG 2.2 AA.
  3. Registrar os resultados, inclusive o que ainda não está conforme.
  4. Colocar acessibilidade no Definition of Done.
  5. Testar com pessoas usando tecnologia assistiva de verdade.

Acessibilidade cognitiva

Boa parte do esforço de acessibilidade vai para deficiência visual e motora. Deficiência cognitiva afeta mais pessoas e recebe menos atenção.

Entram aqui dislexia, TDAH, autismo, ansiedade, declínio cognitivo por idade — e também estados temporários: cansaço, pressa, estresse, uso do celular no meio da rua.

Informação

Interface que funciona para quem está exausto funciona melhor para todo mundo. Este é o caso mais claro de que acessibilidade não é caso de exceção.

O que ajuda

  • Linguagem direta, frase curta, sem jargão desnecessário.
  • Uma tarefa principal por tela.
  • Passo a passo visível em fluxo longo.
  • Erro que diz o que fazer, não só o que está errado.
  • Ação destrutiva com confirmação e com desfazer.
  • Sem limite de tempo, ou com opção de estender.
  • Padrão consistente entre telas.
  • Não depender de memória entre etapas.

O que atrapalha

  • Movimento automático, carrossel que gira sozinho.
  • Formulário longo sem divisão nem salvamento parcial.
  • Mensagem de erro genérica.
  • Sessão que expira sem aviso.
  • Excesso de informação simultânea.
  • Ícone sem rótulo textual.

Colocar no CI, não só no navegador

Verificação que depende de alguém lembrar de rodar não é verificação. O axe roda sobre HTML gerado, sem navegador: 

npm install --save-dev axe-core jsdom
// scripts/check-a11y.js
const { JSDOM } = require('jsdom');
const fs = require('fs');

const axeSource = fs.readFileSync(require.resolve('axe-core/axe.min.js'), 'utf8');

async function verificar(arquivo) {
  const dom = new JSDOM(fs.readFileSync(arquivo, 'utf8'), {
    runScripts: 'outside-only',
    pretendToBeVisual: true,
  });

  dom.window.eval(axeSource);

  const r = await dom.window.axe.run(dom.window.document, {
    runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa', 'wcag21aa', 'wcag22aa'] },
    // Contraste precisa de CSS computado, que o jsdom não faz.
    rules: { 'color-contrast': { enabled: false } },
  });

  return r.violations;
}

Ligue no pipeline com saída diferente de zero em caso de violação. Aviso que não quebra o build é aviso que ninguém lê.

A ordem que funciona

  1. Lint no editor: pega enquanto você escreve.
  2. axe no CI: pega antes do merge.
  3. Lighthouse antes de subir: pega regressão geral.
  4. TalkBack e VoiceOver na entrega: pega o que importa.

Os três primeiros somam cerca de um terço dos problemas. O quarto é o que responde se alguém consegue usar.

O que Ferramentas NÃO Encontram

Ferramentas automatizadas não substituem testes reais.

Elas não identificam bem:

  • Fluxos quebrados.
  • Foco ruim.
  • Experiência ruim.
  • Anúncios confusos.
  • Navegação complexa.

Código que passa no axe e é inutilizável

Os três exemplos abaixo têm zero violação em qualquer ferramenta automatizada. Os três são inacessíveis. 

<!-- 1. Role sem comportamento.
     Tem role, tem tabindex, tem nome. O axe aprova.
     Enter e Espaço não fazem nada: role não traz comportamento. -->
<div role="button" tabindex="0" (click)="salvar()">Salvar</div>
<!-- 2. Nome acessível mentiroso.
     Existe nome, então a ferramenta passa.
     O leitor de tela anuncia "Editar" num botão que exclui. -->
<button aria-label="Editar" (click)="excluir()">
  <mat-icon aria-hidden="true">delete</mat-icon>
</button>
<!-- 3. Ordem de leitura invertida.
     O HTML está impecável. O CSS troca a ordem, e o Tab
     entrega Confirmar antes de Cancelar. -->
<div style="display:flex; flex-direction:row-reverse">
  <button>Confirmar</button>
  <button>Cancelar</button>
</div>

Por que a ferramenta não vê

Ela verifica o que é verificável sem entender a intenção: o atributo existe, o valor é válido, a relação está declarada. Nenhuma delas consegue responder "esse nome descreve o que o botão faz?" ou "essa ordem faz sentido para quem está preenchendo o formulário?".

A conta real

Ferramenta automatizada pega em torno de um terço dos problemas de acessibilidade. É um terço importante, barato e que roda em todo commit — mas é piso, não teto.

Os outros dois terços exigem alguém percorrendo a jornada com teclado e com leitor de tela, perguntando se dá para concluir a tarefa. Não existe atalho para isso.
